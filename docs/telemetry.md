# Telemetry ordering and status

Telemetry is retained as history even when it cannot change the current flight or status. A sample may advance current state when its device timestamp is no older than `TELEMETRY_ONLINE_TTL_SECONDS` at receipt, no more than five seconds in the future, and strictly later than the previous eligible device timestamp. Missing timestamps use the server receipt time. Equal timestamps are duplicates for current-state purposes; out-of-order, stale, and farther-future samples remain historical. Timestamps are stored at PostgreSQL's microsecond precision. A newer terminal sample closes an active flight; an ineligible terminal sample does not.

HTTP status selects the latest eligible timestamp, with the first row winning an equal timestamp; when no eligible sample exists it reports the historical row as offline. Online requires both device and receipt timestamps to remain within the configured TTL, allowing at most five seconds of device clock skew. The telemetry Redis status key expires at the earlier device or receipt deadline; updates are ordered atomically by committed telemetry ID. Redis availability is best effort, so a missing cache key is possible even when HTTP reports online.

MQTT status payloads are JSON objects with a required boolean `online` and an optional string or null `status`, for example `{"online":true,"status":"ready"}` or `{"online":false}` for a last will. Invalid payloads are logged and ignored. This connection-status key is separate from the telemetry status key and expires after the configured telemetry TTL when online or one hour when offline.

Migration 0013 conservatively marks all legacy samples as not accepted: prior records cannot prove they advanced current state, so they remain historical and a fresh sample must re-establish authority. New accepted samples are marked `accepted_for_current_state`; `neurovector.current_drone_telemetry` exposes the latest accepted row per drone. Arrival history must also filter on that marker and still apply device-time, receipt-time and hold-window checks. Deploy migration 0013 before the new backend and avoid mixing old writers during rollout, since old writers do not set the marker.

# 주문 큐 검증 기록

2026-10-23, 운영 데이터와 분리한 임시 PostgreSQL 16·Redis 7.4·Kafka 3.9.1에서 확인했습니다.

## 수정

- 스토어가 `/orders/queue`로 주문을 접수하고 `/orders/jobs/{id}`를 조회합니다.
  처리 중 재주문을 막고, 같은 탭을 새로고침해도 작업 ID로 조회를 이어갑니다.
- 작업 복구를 주기적으로 실행하고 `failed` 작업도 한도 내에서 재발행합니다.
  실행 중인 트랜잭션은 복구 대상에서 제외하며, 이전 시도의 늦은 실패는 무시합니다.
- Redis 캐시 저장 시 조회 시작 때의 세대를 비교해 무효화 이후의 오래된 저장을 거부합니다.
- 주문·상태·결제·환불 변경과 이벤트를 같은 트랜잭션으로 기록합니다.
  outbox 작업자가 Kafka 발행 성공 후 `published_at`을 기록하고 장애 시 다시 시도합니다.

회귀 테스트는 `TEST_DATABASE_URL`과 `TEST_REDIS_URL`을 임시 인프라로 지정해
`cargo test -- --test-threads=1`로 실행합니다. 해당 환경 변수가 없으면 인프라 테스트는
실행되지 않으므로 결과의 통과 숫자만으로 DB·Redis 검증을 판단하지 마세요.
학교 시뮬레이션 전용 ignored 테스트는 이 검증 대상이 아닙니다.

실행 증거와 재현 스크립트는 `/tmp/neurovector-order-qa/`에 보관했습니다.
브라우저는 사용자 프로필과 분리한 임시 Chrome 프로필을 사용했습니다.
현재 앱은 light/dark 시스템 설정과 무관하게 기존 어두운 테마를 표시합니다.

## 적용과 한계

기동 전에 `0008_order_event_outbox.sql`을 포함한 마이그레이션을 적용해야 합니다.
루트 `make migrate` 또는 compose의 migrate 서비스가 순서대로 적용합니다.
기존 감사 이벤트는 이력으로 보존하며, 마이그레이션 후 새 이벤트부터 outbox로 처리합니다.

브로커 장애·재전송으로 같은 이벤트가 여러 번 전송될 수 있습니다. 외부 소비자도
`event_id`로 중복을 제거해야 합니다. Redis 자체 장애로 캐시 삭제가 실패하면 기존 TTL까지
이전 조회 값이 남을 수 있습니다. 운영 DB 적용·배포와 부하 테스트는 수행하지 않았습니다.

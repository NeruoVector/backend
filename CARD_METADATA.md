# Demo payment method metadata

Authenticated customer-session endpoints: GET/POST `/api/v1/auth/cards`, DELETE `/api/v1/auth/cards/{id}`. POST accepts exactly `{"kind":"card"}`, `{"kind":"bank_account"}` or `{"kind":"mobile"}`. No user supplied financial details are accepted; unknown fields are rejected. The server generates four random display digits with the OS CSPRNG and a Korean label for the selected kind. These are demo records, not registrations with a financial institution. Each returned record has `is_demo:true`; the list reports `payment_enabled:false`. Never submit PAN, CVC, expiry, cardholder credentials or payment tokens.

Apply `migrations/0012_customer_card_metadata.sql` before exposing these routes. The table stores owner/record IDs, timestamps, format version, key identifier, a random 96-bit nonce and AES-256-GCM authenticated ciphertext. Kind, generated label and last4 are serialized together and encrypted. Legacy encrypted card notes without kind decode as card for compatibility. AAD binds the format, key identifier, customer UUID and record UUID. Each encryption uses the operating system RNG. Only the authenticated owner can list or delete records; nonowner deletion returns 404.

Supply `CARD_METADATA_KEY` externally as standard base64 encoding exactly 32 cryptographically random bytes. Never commit it or pass it in a URL. The key identifier is SHA-256 of the key; it is internal and is not returned by the API. The configuration Debug representation redacts the key.

Back up the key securely and retain it for the lifetime of the records and database backups. Loss of the key makes the metadata unreadable. This implementation supports one active key, not automated rotation: replacing the key makes existing records unavailable. A rotation requires an explicit, audited decrypt/re-encrypt migration with both old and new keys and fresh nonces; do not overwrite or remove existing rows to resolve a key mismatch.

Without a configured key, GET returns `storage_available:false` only if there are no saved notes; POST fails with 503. Missing/mismatched keys, unsupported versions or failed authentication for existing ciphertext cause GET to fail closed with 503, preserving the records. DELETE remains available to the authenticated owner. An absent or empty key disables storage; malformed nonempty key material prevents startup. Readiness indicates configured key availability, not payment readiness. There is no payment token, payment linkage, checkout authorization or default method selection.
